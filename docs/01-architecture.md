## 1. 这是什么

ClaraCore Server 是一套**部署在服务器上、供团队共用的 MCP 记忆服务**。多个使用者的多个 agent 通过 MCP 协议远程连接，共享分层的记忆与协作上下文。

**一句话定位**：让团队的踩坑经验和工程约定，能被所有人的 agent 在正确的时机自动召回。

比"团队共享记忆"更锐利——后者是模糊的基础设施描述，前者说得清价值在哪。核心载体是**知识卡片**（见 §1.3），不只是零散的记忆条目。

### 1.1 与 ClaraCore Desktop 的关系

**两条独立产品线，不是同一个产品的两个版本。**

| | Desktop（个人版） | Server（团队版） |
|---|---|---|
| 使用者 | 单人 | 团队 |
| 部署 | 本地 Electron 应用 | 服务器 |
| 实现 | JavaScript / Node | Go |
| 数据库 | SQLite（本地文件） | MySQL 等外部数据库 |
| 功能范围 | Memoria + Continuity + InnerLife + Gateway | Memoria + Continuity + Gateway |
| 演进状态 | **继续正常演进，不冻结不废弃** | 新建 |

Desktop 服务的个人场景依然成立，因此这是**产品线扩展**，而不是继任或替代。

### 1.2 共享契约，不共享代码

语言不同注定代码无法复用。两条产品线共享的是**规格**：

- MCP 工具的名称、参数、语义保持一致
- 数据模型的核心概念保持一致（memory / label / link / shared_line）

**理由**：同一个人会同时使用两边，工具语义不一致会造成使用混乱；且个人版数据将来需要能导入团队版。

工具契约以文档 `03-mcp-contract.md` 为共同基准，两边各自实现。

### 1.3 两类一等公民：Memory 与知识卡片

**知识卡片（Card）不是 Memory 的一种子类型，是独立的一等公民实体。**

| | Memory | Card（知识卡片） |
|---|---|---|
| 结构 | 自由文本 + labels | 固定 section（来源 / 提炼 / 理解 / 为什么值得保留 / 何时该想起 / 未解决问题 / 关联） |
| 长度 | 一句话事实 | 一篇复盘（现有卡片普遍 40–60 行） |
| 召回机制 | embedding 语义相似度**推测** | **「未来什么时候该想起它」是作者显式写下的结构化触发条件** |
| 生命周期 | 可 supersede / archive | 有状态（验证期 / 已确认），持续演进 |
| 团队价值 | 个人事实，团队多数不需要 | **踩坑经验与工程约定，全团队都该看到** |

**这是 Server 版价值的核心所在。** Desktop 时期因为 Memoria 装不下长文，采用了「正文在文件、指针存 Memoria」的双层妥协结构（见 `knowledge/cards/README.md`，2026-07-15 约定）。Server 版**不继承这个 hack**，Card 原生落库。

**结构化召回条件是白捡的技术优势**：「何时该想起」由作者显式写下，可以单独建索引、单独匹配，不必依赖向量去猜场景相关性。这是纯语义检索给不了的精度。

典型工作流，与 §8 的空间提升机制严丝合缝：

```
个人踩坑 → 提炼成 Card（个人空间）→ 提升（复制）到团队空间 → 全团队 agent 在对的时机召回
```

## 2. 技术选型

| 组件 | 选型 | 理由 |
|---|---|---|
| 语言 | **Go** | 单二进制部署；真多核并行；长跑内存可控 |
| MCP | **官方 Go SDK** (`modelcontextprotocol/go-sdk`) v1.0+ | 官方 + Google 维护，v1.0 已承诺 API 稳定，Streamable HTTP 完整支持，自带 auth 中间件 |
| 数据库 | **MySQL**（抽象层支持其他） | 运维熟悉度；生态成熟 |
| 缓存/协调 | **Redis（可选）** | 见 §6，必须可降级 |
| 反向代理 | **Nginx** | 已有运维体系 |
| Web UI | **Go 模板 SSR + htmx** | 前端资源 `embed` 进二进制，保住单文件部署 |

### 2.1 为什么是 Go（准确版本）

常见的说法是"JS 扛不住并发"，这不准确。Node 的事件循环处理 IO 密集型并发（本场景 90% 是数据库读写 + HTTP）是强项。

**Desktop 真正扛不住的是 CPU 密集部分**：语义检索的余弦相似度计算跑在 JS 单线程上，一个 agent 发起大范围搜索会独占事件循环，导致**所有其他 agent 一起阻塞**。

Go 在这件事上是天然解：goroutine 跑向量计算，真多核并行，重搜索不影响其他请求。

附带收益（对运维场景价值同样大）：

- **单二进制部署**：`scp` 一个文件 + systemd unit，生产环境无 `node_modules`、无依赖安装、无原生模块 ABI 不匹配
- **长跑内存可控**：常驻服务的刚需
- **清账机会**：Desktop 的很多设计是"本地单用户单进程"假设长出来的，重写是一次性清干净的唯一时机

**为什么不是 Python**：GIL 在 CPU 密集下与 Node 同病；部署依赖管理对运维是纯负债。Python 唯一的绝对优势是本地 AI 生态，而这恰好是 Server 版要砍掉的部分（见 §2.2）。

### 2.2 Embedding 走外部服务

Desktop 唯一的 npm 依赖是 `@xenova/transformers`（本地 ONNX 推理），用于"下载即用、无需另装 Ollama"的开箱体验。

**Server 版不做本地 embedding**，一律走 HTTP：

- Ollama（`/api/embed`，批量输入）
- OpenAI-compatible 接口

纯 HTTP 调用，Go 无任何劣势。本地推理在服务端是负担而非资产。

                    │  │ (Stream   │  (SSR +   │  │

                    │  ┌───────────▼───────────┐  │
                    │  │   Ports (interfaces)  │  │  ← 端口层
                    │  │ Domain Store /        │  │

              ┌────────────────────┼────────────────────┐

## 4. MCP 协议决策

### 4.1 采用 Stateless 模式

官方 Go SDK 的硬约束：**协议版本 `2026-07-28` 只在 `Stateless = true` 时被接受**，没有向后兼容的替代方案。

**决策：`Stateless = true`。**

**收益**：每个请求独立处理，天然支持水平扩展——nginx 后面可以挂 N 个实例任意滚动更新。这正是团队服务需要的。

**代价**：服务端无法主动向客户端发起请求。stateless 下每个请求是临时 session，客户端的响应没有路径回到服务端。

**为什么代价可接受**：

- Memoria / Continuity / Gateway 全部是请求-响应式，不需要服务端推送
- **InnerLife 已被砍掉**——它的"主动开口"机制本质上需要服务端推送，在 stateless 下无法实现。产品判断（企业不需要 agent 有内心活动）与技术约束指向了同一个结论

### 4.2 ✅ 已验证（2026-08-05，详见 `06-poc-findings.md`）

协议版本 `2025-11-25` 在 `Stateless = true` 下**协商正常**，`2025-03-26` 等旧版本同样正常。

**Claude Code 2.1.222 实测连接成功**，走 `initialize` 握手并协商到 `2025-11-25`——2026-07 时"客户端跟不上"的担忧已不存在。

补充发现：`2026-07-28` 废弃了 `initialize` 握手，因此走 `initialize` 路径的客户端协商上限即为 `2025-11-25`。要使用 `2026-07-28`，客户端需改走 `_meta` 无握手路径；**服务端侧 SDK 已就绪，我们无需额外工作**。

### 4.3 Resumability 第一版不做

断线重连补发消息需要自行实现 `EventStore`（SDK 只提供 `MemoryEventStore` 供测试）。且官方文档明确 stateless 模式下的 resumability 语义仍在定义中。

**第一版不实现**，端口层预留 `EventStore` 接口，将来落在 Redis 上（见 §6）。

## 5. 认证与身份模型

### 5.1 核心原则：Token 即身份

**Desktop 的做法（不可沿用）**：agent 身份通过 HTTP header `X-ClaraCore-Agent-ID` 由客户端自行声明，bearer token 只是一个全局开关。任何持有 token 的人可以声明自己是任意 agent。

**Server 的做法**：

```
bearer token  ──▶  TokenVerifier  ──▶  (tenant, user, agent, scope)  ──▶  context
```

- 身份**全部**从 token 反查
- header 中的任何身份声明**一律不信任**
- 实现位置：Go SDK `auth` 包的 `RequireBearerToken` 中间件 + 自定义 `TokenVerifier`（中间件自动处理过期与 scope 校验）

### 5.2 Token 设计

| 规则 | 说明 |
|---|---|
| **一个 token = 一个 agent** | 不是"一个用户一个 token"。多 agent 共用 token 会使审计无法回答"谁写的"，且吊销粒度过粗 |
| **一个 agent 可有多个有效 token** | 平滑轮换的前提。单 token 模型下轮换必然中断服务 |
| **只展示一次** | 创建时明文返回一次，库中只存 hash |
| **记录 `last_used_at`** | 用于识别可安全吊销的 token，Web 上直接显示"最后使用于 X 前" |
| **带可识别前缀** | 便于日志脱敏与泄露扫描 |

**轮换流程**：签发新 token → 各设备逐个更新 → 观察旧 token 的 `last_used_at` 不再变化 → 吊销旧 token。

### 5.3 两套会话互不干扰

| | 载体 | 用途 |
|---|---|---|
| Web 登录态 | session / cookie | 人操作管理界面 |
| MCP 连接 | bearer token | agent 调用工具 |

Web 会话过期不影响 agent 连接；token 吊销不影响网页登录。

### 5.4 账户体系

**管理员分配账号，非自助注册。** 封闭式团队部署，因此不需要邮箱验证、密码找回、注册防刷等一整套流程。

流程：管理员创建用户 → 分配初始密码 → 首次登录强制改密 → 用户自助创建 token → 复制 MCP 配置片段接入。

## 6. 可插拔组件与 Redis 的位置

### 6.1 降级原则

**Redis 是可选的，不是启动依赖。** 未配置 Redis 时，所有端口使用内存或数据库的默认实现，系统功能完整。

这保住了单二进制部署的核心优势——想轻量试用的人不需要先搭一套 Redis。

### 6.2 端口与实现

| 端口 | 默认实现 | Redis 实现 | 何时需要 Redis |
|---|---|---|---|
| `Cache` | 进程内有界 LRU（已用于 embedding） | Redis | 多实例部署 |
| `Embedder` 缓存 | `hash(text+model)` + TTL，默认 1024 条（已实现） | Redis | 多实例共享命中与跨重启保留 |
| `RateLimiter` | 进程内计数 | Redis 滑动窗口 | 租户级配额、多实例 |
| `Locker` | 数据库行锁 | Redis 分布式锁 | **多实例部署时必须** |
| `SessionStore` | 数据库 | Redis | 多实例部署 |
| `EventStore` | 不实现 | Redis | 将来做 resumability 时 |
| `TaskQueue` | 同步执行 | Redis 队列 | embedding 批量计算、大批量导入 |

## 7. 从 Desktop 吸取的教训

以下均为 Desktop 代码中的真实问题，Server 版从一开始规避：

| Desktop 的问题 | Server 的做法 |
|---|---|
| 身份靠 header 自行声明 | token 即身份，见 §5.1 |
| 单一全局 token，轮换即全断 | 多 token 并存，独立签发/吊销，见 §5.2 |
| 语义检索全表扫 + 单线程算余弦 | 两段式检索：**粗筛**（标签/时间/全文缩小候选）→ **精算**（并行计算相似度）；向量能力隔离在 `VectorIndex` 端口后 |
| 时间戳带本地时区（`localDateForTimezone`） | **存储层统一 UTC**，时区只在展示层处理。多设备跨时区是本项目的常态 |
| 作用域字段带默认值（`DEFAULT 'local-user'`） | 作用域字段**不给默认值**，缺失即报错，不让 bug 静默 |
| SQL 触发器承载业务逻辑 | 逻辑上移应用层，保证跨数据库可移植 |
| spawn SQLite CLI 子进程 | 标准连接池 |
| 35 张表在单一 schema 中逐步堆积，无整体划分 | **一开始就分域**：核心域（memory/link/label/space）/ 运行时（trace/session/job）/ 治理（tenant/user/token/audit） |

## 8. 团队场景的新问题

以下问题 Desktop 从未面对，需在 `02-data-model.md` 中解决：

1. **记忆的共享边界** — 已定方向：三层空间（个人 / 项目 / 团队），权限只分读写，不做复杂 RBAC
2. **作者与可见性** — 多人场景下每条记忆需要 author 与可见范围，Desktop 的单一 `agent_id` 字段不足以表达
3. **并发冲突** — 多 agent 同时更新同一条记忆，需要版本号 / 乐观锁
4. **配额与限流** — Desktop 的 `maxActivePerAgent` 只防自己卡自己；团队场景需要租户级配额
5. **冷启动** — 见 §8.1，这是团队产品的生死问题

### 8.1 冷启动：团队版的生死问题

个人版第一天是空的没关系，用一个月就长满了。**团队版第一天是空的，就等于没人用，然后永远是空的**——团队知识产品基本都是这么死的。

团队与个人的根本差异：个人是「慢慢和 agent 一起积累」，团队则**已经存在大量存量知识**（odoc 运维知识库、Atlas、以及散落的各类 md 文档）。能否把存量接进来，决定这个产品能不能启动。

因此**摄取能力不是次要的运维功能，是第一版必须有的核心能力**。

#### 8.1.1 纳入 vs 连接：判断标准只有一条

> **那份知识还在被原系统维护吗？**

| 来源 | 方式 | 理由 |
|---|---|---|
| **odoc**（活的，持续更新） | **连接** | 复制进来两边必然漂移。odoc 里更新了服务器 IP 而镜像还是旧的，agent 拿过期信息去连生产——**比没有更危险** |
| **散落的 md 文档**（已无人维护） | **纳入** | 原处已是死的，搬进来是给它第二次生命 |
| **Atlas**（演进中） | 取决于它是否继续独立存在 | 待定 |

#### 8.1.2 摄取 ≠ 粘贴

**把 md 整篇塞成 Memory，会直接毁掉本产品的核心价值。**

Card 的价值在于「提炼 + 理解 + 何时该想起」，而现成文档**恰恰没有这三样**——它只有原始信息。整篇导入的结果是一堆检索不准的长文本，`card_recall` 什么都命不中，因为没有触发条件。

摄取必须是两步，且第二步正是 agent 该干的活：

```
摄取(ingest) ──▶ agent 提炼(distill) ──▶ 人审核确认 ──▶ Card
   原文档          生成提炼/理解草稿/召回条件       status: draft → active
```

**质量闸门**：沿用 `knowledge/cards/README.md` 的既有标准——「理解」栏为空的卡只是摘要。落到团队版即：**agent 提炼的草稿必须有人确认才能从 `draft` 转 `active`**；无人认领的长期停留在 `draft`，不进默认检索。

这样既解决冷启动，又不会让库里灌满没人负责的垃圾。

#### 8.1.3 外部源连接：索引同步，不做实时代理

Go SDK 同时提供 server 与 client API，因此本服务可以**一边对 agent 当 server，一边对外部 MCP 源当 client**（MCP 网关/聚合模式）。

两种连接方式的取舍：

| | 实时代理 | **索引同步（采用）** |
|---|---|---|
| 做法 | 每次检索转发给外部源 | 定期抓取内容做 embedding 存本地，**正文留在原处** |
| 排序融合 | ❌ 外部结果无可比分数，只能分组展示 | ✅ 统一向量空间，真正融合 |
| 延迟 | 每次检索叠加外部调用 | 本地检索 |
| 外部源宕机 | 检索直接缺一块 | 索引仍在，正常返回（标注可能过期） |
| 前提 | 外部源有 search 即可 | **外部源必须可枚举**（list/export 类工具） |

**决策：索引同步。** 可枚举这个前提是成立的——外部源（odoc/Atlas）均为自有服务，缺少枚举接口可以直接补上。

**两条硬规则**：

1. **服务级凭证**。ClaraCore 用单一服务账号连接外部源。前提是外部源本身无细粒度权限隔离（odoc 已确认如此）。若将来接入有权限分层的外部源，此决策必须重新评估——否则等于把受限信息平权暴露给全体成员。
2. **外部内容一律只读**。不可编辑、不可提升、不可加 label。它在库中是**镜像而非副本**。要基于外部内容做提炼，应**新建一张 Card**并将 `source` 指向原条目，而不是修改镜像。

#### 8.1.4 分版本落地

| 版本 | 范围 |
|---|---|
| **第一版** | md/markdown 批量摄取 → agent 提炼 → 人审核 → 落成 Card。冷启动的底线 |
| **第二版** | 外部 MCP 源连接器（odoc、Atlas），索引同步，只读镜像 |

## 9. 部署形态

```
  systemd
     └── claracore-server (单二进制，含 embed 的 Web 资源)
              ├── :PORT/mcp    ← MCP Streamable HTTP
              └── :PORT/       ← Web 管理界面

  nginx ── TLS 终结 ── 反代到上述端口
  MySQL ── 外部
  Redis ── 外部，可选
  Embedding ── 外部 HTTP（Ollama / OpenAI-compatible）
```

### 9.1 Nginx 必须的配置

> **已按 PoC 实测修正**（2026-08-05）：stateless 模式下 `GET` / `DELETE` 返回 `405`，**不存在 GET 建立的 SSE 长连接**，全部交互是 POST 请求-响应。但 POST 的**响应体仍是 `text/event-stream`**（实测 `Content-Type: text/event-stream` + `Transfer-Encoding: chunked`），因此关闭缓冲仍然必要，长连接保活则不需要。

```nginx
location /mcp {
    proxy_pass              http://127.0.0.1:PORT;
    proxy_http_version      1.1;
    proxy_buffering         off;          # 必须：响应体是 event-stream
    proxy_cache             off;
    proxy_set_header        Connection '';
    chunked_transfer_encoding on;
    # proxy_read_timeout 无需拉长：stateless 下没有 GET 长连接
}
```

服务端响应同时应带 `X-Accel-Buffering: no`。

**逃生舱**：若部署中仍遇到缓冲问题，`StreamableHTTPOptions.JSONResponse = true` 可让响应改为 `application/json`，nginx 即无需任何特殊配置——代价是失去流式返回能力。见 `06-poc-findings.md` §4.2。

## 10. 明确不做

| 不做 | 原因 |
|---|---|
| **InnerLife** | 企业场景不需要 agent 的内心活动；且 stateless 下无法实现主动推送 |
| **Web 上凭空创建记忆 / 自由编辑已确认内容** | 只做只读查看 + 管理动作（删除/改可见性/查作者）。开这个口子会产生两套业务逻辑，以及语义与 agent 写入不一致的手工记忆。<br>**例外——草稿审核**：审核 agent 提炼的 Card 草稿（可修改后确认）**是要做的**（§8.1.2）。二者的区别在于：审核发生在明确的摄取流程内、针对 `draft` 状态、有原文可对照；而不是让人在库里随手写。 |
| **本地 embedding 推理** | 见 §2.2 |
| **复杂 RBAC** | 只分读写。角色体系的复杂度不匹配当前场景 |
| **自助注册流程** | 管理员分配账号，见 §5.4 |
| **前后端分离** | 会把 npm 生态与构建链请回来，抵消单二进制部署优势 |
| **复用 Desktop 代码** | 语言不同，且 Desktop 携带大量本地单用户假设。共享契约而非代码 |

### 11.1 已决策（2026-08-05）

| 议题 | 决策 | 关键推论 |
|---|---|---|
| **Agent 归属** | 属于**人**。一个用户拥有多个 agent，权限配置在用户身上，agent 继承用户的全部权限 | **agent 是审计维度，不是权限维度**。token 绑 `(user, agent)`，鉴权只查 user 的空间授权；token 表与权限表彻底解耦 |
| **权限粒度** | 空间级别，只分**读 / 写**。不做细粒度、不做 RBAC | 复杂度不匹配当前场景，先简单 |
| **空间提升** | 允许，方式是**复制**（非移动） | 记录 `copied_from` 来源链接以便追溯，但**不做自动同步**——两份各自演进。原件更新时可提示衍生副本可能过时 |
| **跨空间检索** | **默认跨空间**，权限过滤**下推到 SQL**，结果**标注来源空间** | 过滤绝不能在应用层做（性能 + 信息泄露）；来源空间让 agent 能判断权威性（团队 = 已达成共识，个人 = 个人经验）；工具参数支持显式 `spaces: [...]` 限定作为逃生舱 |
| **内容类型** | Card 作为独立一等公民实体，不是 Memory 的子类型 | 见 §1.3，显著影响表结构 |
| **冷启动 / 摄取** | 摄取是第一版核心能力，非次要运维功能 | 见 §8.1。团队有存量知识，接不进来产品无法启动 |
| **纳入 vs 连接** | 按「原系统是否仍在维护」判断：odoc 连接，死文档纳入 | 活系统复制进来必然漂移，过期的运维信息比没有更危险 |
| **摄取流程** | 摄取 → agent 提炼 → **人审核确认** → Card | 直接粘贴原文会毁掉 Card 的召回价值；审核是质量闸门 |
| **外部源连接方式** | **索引同步**（正文留原处），非实时代理 | 可融合排序 + 外部宕机不影响检索。前提「可枚举」成立——外部源均为自有服务，缺接口可补 |
| **外部源凭证** | 服务级单一账号 | odoc 已确认无细粒度权限隔离。**接入有权限分层的外部源时此决策必须重评** |
| **外部内容权限** | 一律只读，是镜像不是副本 | 要提炼则新建 Card 并将 `source` 指向原条目 |

### 11.2 剩余待定

**2026-08-06 全部拍板，本节已无未决项**（完整口径见 `HANDOFF.md` §已拍板）：

- [x] **项目空间的成员**：**显式加入**。创建时只有创建者有权限，其他人需显式授权。
- [x] **谁有权提升**：**任意有目标空间写权限者**。promote 本质就是一次写入，不引入新权限概念。团队知识库的死法不是垃圾太多而是没人往里放，加一道审批就是加一道不写的理由——质量用 Card 的 `status` 挡（内容成熟度），不用权限挡。
- [x] **检索排序中空间的权重**：**只做 tie-break，不可配**。相关性优先，仅当两条分数接近时才按 team > project > personal 决胜。把来源当排序主键会让个人空间里的精准命中排在团队空间的勉强沾边之后，直接拉低检索质量。
- [x] **数据库最低版本**：**MySQL 8.0**（ngram 全文解析器、CTE、JSON 函数、生成列唯一索引均需要）。实际验证环境 8.0.36。
