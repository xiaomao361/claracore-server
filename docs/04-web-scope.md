## 1. 为什么需要 Web

### 1.1 首要理由：消除黑盒

个人版里，你自己就是 agent 的唯一使用者，它读了什么写了什么你心里有数。**团队版不是**——成员看不见 agent 在读什么、写了什么、召回了哪张卡，整个过程就是黑盒。

**黑盒的直接后果是没人敢把团队知识放进来。** 这不是体验问题，是采用率问题。

因此 Web 的第一职责不是"管理"，而是**让 agent 的工作过程对人可见**。

### 1.2 次要理由：治理面归位

`03-mcp-contract.md` §1.1 已确立工作面 / 治理面的切分。从 MCP 移出的操作（导入导出、合并建议、休眠归档、标签别名、维护审计）需要落地入口，Web 就是它们的归属。

### 1.3 Agent First 依然成立

需要 Web 不等于放弃 Agent First。二者的分工是明确的：

| | 归属 | 内容 |
|---|---|---|
| **工作面** | MCP（agent 用） | 创建、检索、更新、召回、关联、提升 |
| **治理与可见性** | Web（人用） | 观察 agent 做了什么 + 人才该做的决定 |

参照物：GitHub 有完整 Web 界面，但它依然是 API First。

### 1.4 铁律：共用领域层

**Web 与 MCP 必须调用同一套领域层，不允许各写一套业务逻辑。**

Web 是 `01-architecture.md` §3 中与 MCP Host 并列的另一个 Host，二者共享 Auth / Core Domain / Ports。任何"Web 专用的写入路径"都是设计事故。

## 2. 可见性边界（本文档最关键的设计）

团队场景存在一个真实张力：

- 完全不可见 → 黑盒，没人敢用
- 完全可见 → 我能看到同事的 agent 读了什么，**这是监控**

### 2.1 划分原则

> **写入是协作行为，读取是私人行为。**

| 活动 | 谁可见 | 理由 |
|---|---|---|
| **我自己 agent 的全部活动**（读 + 写） | 我自己，完整可见 | 自己的 agent 必须可审视 |
| **共享空间（team/project）的写入** | 该空间全体可读成员 | 谁往共享知识里加了什么，是协作必需的透明度 |
| **他人在个人空间的任何活动** | 不可见 | 个人空间的封闭性是敢于记录的前提 |
| **他人的读取/召回记录** | **不可见** | 看别人读了什么等于监控。读取行为不产生协作价值，只产生窥视 |
| **全部活动（含读取）** | 仅管理员，且限于明确的审计场景 | 见 §2.2 |

### 2.2 管理员审计的自我约束

管理员出于安全审计需要，可以查询包含读取行为在内的完整日志。但：

- **审计查询本身必须被记录**（meta-audit），且该记录管理员不可删除
- 审计入口与日常管理页面分离，需二次确认

理由：一个能悄悄查看所有人读取记录的管理员账号，会让整个产品失去信任基础。让审计留痕不是防坏人，是让好人可以自证。

| 4 | **活动流** | **消除黑盒的核心页面**。agent 的工具调用时间线：调了什么、命中了哪些内容、写入了什么。按 §2 规则过滤 | `trace` |

**页面 6 的关键细节**：创建 Token 后**直接生成可复制的完整 MCP 配置块**（地址已填、token 已嵌入），用户粘贴即用。不要让人自己拼 JSON——接入体验的差距全在这里。同时 Token 明文**仅此一次展示**。

### 3.4 视觉设计节点（2026-08-11 已验收）

Web 的功能闭环先以朴素 SSR 页面验证；生产视觉已在 [ClaraCore Server — Product Direction 01](https://www.figma.com/design/6ObFIgv8rQVrZnEX5WdaMr) 完成当前范围的设计与结构验收。

- 基准与页面：`03 · Web Workspace` 为工作台基准；`04 · Activity Feed`、`05 · Card Review`、`06 · Content Browse` 为三张生产页；`07 · Responsive & States` 覆盖 390px 窄屏与加载、空、错误、焦点等状态。
- Web 骨架：1440 桌面视口、持久左侧导航、顶部面包屑/搜索/环境状态、紧凑指标区、筛选表格和双栏内容。390px 是同一套 Web 的窄屏降级，不是独立 App 结构。
- 产品语气：温暖、可信、低装饰；共同线是核心工作模块，但不占据整页 hero。大标题、居中叙事和舞台式三块布局已否决。
- 设计系统：3 个变量集合、61 个变量、9 个文字样式、1 个效果样式；14 个组件/组件集共覆盖 61 个形态，包含按钮、表单、导航、分页、表格行、反馈状态及三类业务列表项。
- 验收结果：生产页与组件没有默认命名、占位文案或未绑定的填充/描边；统一使用 Noto Sans SC；390px 根容器无横向溢出；交互控件有焦点态，状态不只依赖颜色；关键文字/背景组合对比度均不低于 5.0:1。

> **实现进度（2026-08-28）**：生产视觉已同步到 Go SSR 的全部现有页面族。共享 shell、语义 token、指标卡、筛选工具栏、表格、活动流、审核、内容浏览、共同线、治理表单、空状态、登录与接入页已统一；复制 token / MCP 配置是渐进增强，JavaScript 不可用时仍可手动选择。自动化浏览器已逐页核对 1440 / 390px 无整页横向溢出，表格在自身容器内滚动；目标服务器上的真实身份、真实数据、键盘/读屏与业务验收仍由用户完成。Code Connect 等到 SSR 组件与 Figma 组件形成稳定的一一映射后再接，当前不为映射而先造抽象。

> **看板补齐（2026-08-29）**：概览不再只陈列内容总量。共同线采用租户级精确口径，知识质量只统计调用者可读空间中的 active 卡片，索引状态按租户/当前模型统计。自动上下文区展示近 30 天“已关联反馈选择 / 全部选择”，只有能匹配同租户、本窗口真实选择的匿名 `contextId` 才计覆盖；放弃按无相关证据、歧义、语义不可用、超时、Shared Line 未就绪和其他/旧记录六个固定低基数类别归因。分类只用于运行排障和语料治理，主动提交的 outcome 仍不解释成准确率。四组信号任一读取失败都只降级该组并保留首页其他内容。所有详情入口仍是原生链接，标题层级为 H1 → H2 → H3，没有引入自定义交互组件。

> **协作脉搏（2026-08-29）**：看板新增近 7 个 UTC 自然日的共享写入序列、去重活跃成员、去重活跃 Agent 与最近贡献。可见性沿用活动流的“写入是协作、读取是私人”边界，并在 SQL 聚合前限定为调用者可读的 team/project 空间；个人空间、不可读项目、失败操作、读取/召回和窗口外事件都不进入统计。该组衡量采用情况，不解释为知识质量；查询失败只显示局部提示，不影响概览其他区域。

> **运行容量补齐（2026-08-29）**：管理员系统页复用 `/readyz` 的迁移检查，不把启动时记住的版本冒充当前真相；schema 漂移会明确标成不能安全接流量。连接池只显示 `database/sql` 的进程内安全摘要：当前使用/上限、打开、空闲、累计等待时长和累计回收，不显示 DSN、主机、账号或查询。80% 占用只作为当前注意信号；累计等待是本次进程生命周期内的历史计数，不解释为当前延迟。

> **租户容量基线（2026-08-29）**：管理员主动打开系统页时，Server 最多等待 3 秒，在 repeatable-read 只读事务中按当前租户聚合成员、Agent、空间、Memory、Card、召回条件、标签、关联、共同线、embedding、外部镜像与活动审计。页面只收到计数和 `OCTET_LENGTH` 逻辑载荷，不收到正文、实体或 actor 标识；查询有专用 tenant-leading 索引，且不进入高频 `/metrics`。逻辑载荷不含 InnoDB 行/索引开销、空闲页、binlog、备份与副本，因而是未来制定存储策略的可信应用基线，不是物理磁盘、成本或账单配额。当前只观测，不执行硬限制。

> **HTTP 健康窗口（2026-08-29）**：系统页新增本实例最近 5 分钟已完成的业务请求、4xx、5xx、panic、当前在途、平均耗时与 P95 直方图上界。三个健康探针不计入，避免检查频率掩盖真实业务；任一 5xx 或 panic 触发注意态，4xx 只陈列不解释为服务故障。实现只有 5 个分钟桶和 10 个固定延迟桶，不按路由、request ID、用户或租户分组，内存常量且不持有访问内容。窗口随实例重启清空；多实例页面只代表当前实例，不是集群汇总或外部监控替代品。

> **备份状态补齐（2026-08-29）**：备份 verifier 成功后原子写入不含正文、连接信息或凭据的 0600 JSON 回执。系统页只读取这一个最大 8 KiB、非符号链接、字段严格的文件，并用当前实例时间重新计算备份年龄；页面请求不会扫描备份目录、解压归档或重新哈希大文件。回执缺失、损坏、过期或时间异常均显示注意态；完整性通过仍明确要求隔离恢复演练。

> **Web 写入资源边界（2026-08-29）**：所有浏览器写请求只接受 `application/x-www-form-urlencoded`，入口先用 `http.MaxBytesReader` 限制为默认 1 MiB，再统一 `ParseForm`；超限返回 413、媒体类型错误返回 415，handler 不会继续执行。这样不会让 `FormValue` 吞掉解析错误后以部分字段执行治理动作。MCP JSON 使用独立的 SDK 请求体限制，不经过这条 Web 中间件。

> **浏览器与缓存边界（2026-08-29）**：所有非静态 Web 响应（含登录、重定向、错误和一次性 token/密码页面）均为 `no-store, private`、`noindex`。CSP 以 `default-src 'none'` 起步，只开放同源 script/style/font/connect、同源或 data image 与同源 form，明确禁用 object、frame ancestor、base、manifest 和 worker；同时提供 DENY frame fallback、no-referrer、Permissions Policy、COOP/CORP 与 nosniff。页面仍只使用外部同源 JS/CSS，不加入 inline 例外。`/static/` 文件名未带内容 hash，因此只允许 300 秒公共缓存，不能标记 immutable。

> **功能补齐（2026-08-28–29）**：Web 审核写边界已收紧为 draft-only，并把版本号带到提交端做乐观锁；active / deprecated 只读且不再出现编辑入口。队列的批量能力只允许把人明确勾选的草稿标记为不需要，每批 1–50 张、事务内全量版本与权限校验、任一冲突整批回滚；不存在批量发布。停用成员、重置密码、吊销 token、撤销权限、归档共同线与标记草稿不需要均有明确二次确认。共同线、活动、审计与内容浏览的增长路径和返回上下文已补齐；系统状态页只陈述真实装配与降级。Redis 已实际用于多实例共享 embedding 缓存、索引短租约和每 agent/租户 MCP 预算，并显示实时连通状态；存储与成员已有只读逻辑容量基线，但尚未制定或启用硬配额、计费策略。

## 5. 技术要点

- **Go 模板 SSR + htmx**：局部刷新（审核队列、活动流轮询）用 htmx 即可，不需要 SPA
- **静态资源 `embed`**：CSS/JS/字体全部编译进二进制，保住 `scp` 单文件部署
- **Session**：当前固定存数据库，保证多实例即时吊销；Redis 目前只承担可降级的 embedding 共享缓存与索引短租约
- **密码**：argon2id
- **与 MCP 的会话隔离**：Web 用 session/cookie，MCP 用 bearer token，互不影响（`01-architecture.md` §5.3）
- **活动流的数据来源**：`audit_logs` 一张表按 `kind=trace | governance | meta_audit` 分类；普通查询按 §2.1 规则下推过滤条件到 SQL，**不在模板层过滤**
- **统一埋点**：24 个 MCP 工具都从同一个审计注册装饰器进入；Web 已认证写操作统一在 `requireUser` 边界记录。元数据用强类型白名单摘取，只允许 ID、计数、版本与语义标志，不序列化 query、situation、Shared Line 摘要/下一步、正文、密码、token 或错误文本
- **管理员完整审计**：GET 只展示确认页；POST 先写 `admin.audit.query` 的 meta-audit，再查租户全量。meta-audit 写失败时 fail closed，不执行完整查询
- **保留期**：治理与 meta-audit 长期保留；后台清理 worker 启动时立即执行、之后每 24 小时运行，只按 `kind=trace` 分批删除 30 天前记录

> **验证边界（2026-08-11）**：`0006` 已应用到 development MySQL，完整 `make itest` 已验证活动查询、分页、租户隔离与保留期。真浏览器用隔离临时租户验了 `/activity` 与 `/admin/audit` 二次确认/meta-audit，并验了默认桌面和 390px 窄屏；期间发现的整页水平溢出已改为导航/宽表局部滚动。这些仍是开发环境证据，不代表部署或生产验收。

## 6. 待确认

**2026-08-06 全部拍板。**

- [x] **活动流的保留期**：**拆成两类**。「活动流」现在混了两种东西——① 治理审计（谁授权了谁、谁吊销了 token、谁把卡片提到了团队空间）：量小、价值不随时间衰减，**长期保留**；② 调用 trace（每次 MCP 工具调用）：量大、几天后没人看，**30 天滚动删除**。用同一个保留期卡两者，不是磁盘白烧就是审计记录被过早删掉。不做租户级可配——可配项一开口就得配管理界面、校验和清理任务适配，而第一版没人会去调它。
  <br>**2026-08-11 已落地**：`audit_logs.kind` 把两类记录分开，`DeleteTracesBefore` 的 SQL 固定只删 `trace`；服务启动立即清理一次，之后每 24 小时按 1000 条一批抽干 30 天前的 trace。治理与 meta-audit 不进入删除路径。
- [x] **审核权限**：**任意有该空间写权限者，含摄取发起人自己**。与 promote 一致，不引入新权限概念；审核就是一次带写权限校验的 `status` 更新，没有独立的审核实体。发起人能审自己那批——内容是机器扒的不是他写的，他做的是校对，不是自己给自己盖章。不采用「四眼原则」：某个项目空间只有一个人有写权限时会直接死锁。
- [x] **批量审核边界**：**只批量标记不需要，不批量发布**。人必须逐项勾选当前页草稿；服务端每批最多 50 张，在同一事务内逐项确认 tenant、可写空间、draft 状态和版本，任一项变化则整批不落库。发布需要补齐理解与召回条件，仍保持逐张审核。
- [x] **概览页的"团队近期动态"**：**只展示共享空间的新增/更新卡片**，不含 memory。memory 量大且对别人基本无意义，刷进动态会把卡片淹掉。个人空间一律不进动态——封闭性是用户敢随手记的前提。
- [x] **管理员是否等同于租户 owner**：**单一 admin 角色**。`users.role` 只有 `admin` / `member`；admin 管治理面（建用户、发 token、建空间、授权），member 用知识面。空间内部不再分级——有写权限的人就是平等的参与者。几十人规模下，空间管理员这一层只会制造「找不到人审批」。真需要时再加是加法，先加了要拆是减法。
- [x] **摄取任务的失败处理**：**保留成功项 + 列失败清单**（带源路径与失败原因）。关键前提是**摄取必须做成幂等**（同一源产生同一张卡片 → upsert），这样「重试失败项」就退化成「整批再跑一次」，不需要任务项状态表。幂等本来就是摄取的必备性质——源文档会更新，本来就要重扫。
  <br>**2026-08-10 已落地**：幂等锚点是 `uk_cards_source (space_id, source_key)`（0005 迁移），由**数据库**保证而非应用层先查一次。三分支：没有→新建、内容变了→只更新标题与原文、内容没变→**一步不走**。失败清单带源路径与原因。实测：ClaraCore 自己的 `docs/` 首次 6 created，原样重跑 6 unchanged，改一份后 1 updated / 5 unchanged。详见 `HANDOFF.md` §摄取。

## 7. Web 开工时已解决的密码哈希边界（2026-08-10）

**当时的问题**：领域层不做密码哈希，而旧接口让调用方直接传 `PasswordHash`，没有可靠路径创建真正可登录的用户。

旧的 `governance.CreateUserInput.PasswordHash` 由调用方传入，集成测试里曾塞入 `"$argon2id$e2e$fake"` 这种假值。领域层不读配置（铁律），而 argon2id 的 memory / time / parallelism 参数属于配置——因此领域服务应依赖纯基础设施端口，不能直接读取参数或依赖算法实现。

落地形态（`05-code-structure.md` §3.1 的「纯基础设施接口」）：

```go
// internal/ports/hasher.go —— 签名里没有任何领域概念
type PasswordHasher interface {
    Hash(plaintext string) (string, error)
    Verify(plaintext, hash string) (bool, error)
    NeedsRehash(hash string) (bool, error)
}
```

领域服务通过这个端口完成创建、校验与升级判断，Host 只负责装配配置。**`Verify` 与 `NeedsRehash` 必须留在同一个实现里**：前者按 PHC 串中的历史参数做常数时间校验，后者只允许逐项增强，不能把更强或不可比较的存量哈希降级。

这是 Web 的第一刀绕不开的东西：没有它，登录页和成员管理页都是空壳。

> **2026-08-10 已还清**：`internal/ports/hasher.go` + `internal/adapters/crypto/argon2id.go`。参数走 `config.Password`（`CCS_ARGON2_*`）。
>
> 落地时多改了一处：`CreateUserInput` 从 `PasswordHash` 改成明文 `Password`，由 Service 内部调 hasher。原设计让调用方自己哈希，结果是集成测试里塞了一堆 `$argon2id$e2e$fake` 这种永远验不过的假值，而**没有任何地方能真正创建一个能登录的账号**——欠账不是「还没写哈希实现」，是「这个形状本身让人绕过了它」。
>
> **2026-08-31 参数升级已落地**：成功登录会渐进升级逐项较弱的哈希。更新以“旧哈希 + 认证版本”做 CAS；若并发改密或停用，旧登录重新读取后必须再次通过验证，否则返回统一登录失败且不签发会话。另一个实例已经完成同一升级时则可继续登录。
