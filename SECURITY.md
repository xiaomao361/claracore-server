# Security Policy

## Supported versions

Until stable releases are published, security fixes target the current `main` branch. After versioned releases begin, this table will list supported release lines explicitly.

## Reporting a vulnerability

Please use GitHub's **Report a vulnerability** private security-advisory flow for this repository. Do not open a public Issue for an exploitable vulnerability.

Include the affected version or commit, deployment shape, reproduction steps, impact, and any suggested mitigation. Remove real credentials and personal or production data from logs and screenshots.

We will acknowledge a complete report as soon as maintainers are available, coordinate validation and remediation privately, and publish a disclosure only after affected operators have a reasonable upgrade path.

## Operational security notes

- Run the application as a dedicated non-root user behind HTTPS.
- In production, set `CCS_ENV=production`, `CCS_WEB_SECURE_COOKIE=true`, and an explicit HTTPS `CCS_PUBLIC_MCP_URL`.
- Keep the application bound to loopback and configure nginx to set `X-Real-IP` from `$remote_addr`; the application ignores forwarded client addresses from non-loopback peers.
- Bind `CCS_METRICS_ADDR` only to a dedicated loopback port and keep the shipped nginx `/metrics` denial. The metrics listener has no application authentication because it is a host-local machine interface; never expose it through a public or shared reverse proxy.
- In multi-instance deployments, set a unique opaque `CCS_INSTANCE_ID` on each process. Probe responses expose it publicly, so use only a non-sensitive label; never encode hostnames, internal topology, tenant data, or credentials.
- Validate `deploy/claracore-server.rules.yml` with `promtool check rules` before loading it, merge the example into the existing Prometheus configuration instead of replacing organization-specific retention or Alertmanager routing, and keep the scrape target on loopback.
- Run `make security` with network access before every release. It pins the scanner implementation while querying the live Go vulnerability database and fails closed if findings or database access prevent a clean result. `package-release.sh` repeats symbol-level analysis against the exact Linux binary and includes `BUILDINFO.txt` plus `VULNERABILITY_SCAN.txt` in the signed manifest. That receipt is a build-time snapshot, not a promise that no vulnerability will be disclosed later; rescan supported artifacts after relevant advisories or toolchain updates.
- Keep the pinned `go-licenses` check for both supported Linux architectures. Unknown or forbidden licenses block the build; the release bundles `THIRD_PARTY_LICENSES.csv`, an assembly-only review receipt, required license/notice documents, and the source that the MPL-2.0 MySQL driver requires on redistribution. Treat automated classification as evidence, not legal advice: manually review new reciprocal, restricted, unknown, or non-assembly native dependencies before release.
- Keep the pinned `cyclonedx-gomod` binary SBOM gate for both supported Linux architectures. The generated CycloneDX 1.6 document must match the exact packaged binary SHA-256, Go build information, linked module set, standard-library version, dependency graph, and target `linux/amd64` or `linux/arm64` PURLs; host-platform qualifiers, missing components, random serial/timestamp fields, or build-machine absolute paths fail the release. An SBOM is an inventory snapshot, not a vulnerability result, license decision, reproducible-build claim, or publisher attestation.
- Keep `BUILD_PROVENANCE.intoto.json`, `BUILD_REPRODUCIBILITY.json`, `SOURCE_MANIFEST.sha256`, and `BUILD_INPUTS.sha256` in every release. The release builder must compile with two separate empty Go build caches and fail unless both binaries match byte-for-byte; the receipt is deliberately limited to same-host/same-toolchain reproducibility and is not evidence of hermetic or independent rebuilding. The packaged binary's configuration-free `-verify-provenance` path must bind the in-toto/SLSA statement subject to its own bytes and verify the target, Go/source identity, input manifests, bounded reproducibility result, and other supply-chain byproducts before deployment. The statement is authenticated indirectly by the inner manifest, archive checksum, and pinned-key Ed25519 signature; it is not a DSSE envelope. The repository's local builder is neither hosted nor hardened, so do not claim a SLSA Build Level without separate infrastructure evidence and a documented threat model.
- Keep `CCS_LOGIN_RATE_LIMIT` and `CCS_LOGIN_RATE_WINDOW_SEC` enabled. Redis shares login counters across instances; without Redis, each process retains bounded local protection.
- Raising Argon2id parameters upgrades component-wise weaker stored hashes after a successful login. The update compares both the previously verified hash and authentication generation, so it cannot overwrite a concurrent password reset. Lower or incomparable settings never rewrite a stronger stored hash; review parameter changes deliberately rather than expecting an automatic downgrade.
- Web sessions are server-side, token-hashed, and bound to the user's persisted authentication generation. Password changes, administrator resets, and account disable transitions advance that generation in addition to deleting known sessions; do not remove the generation comparison, because deletion alone cannot revoke a login that inserts immediately after the delete.
- Keep `CCS_MCP_RATE_LIMIT`, `CCS_MCP_TENANT_RATE_LIMIT`, and `CCS_MCP_RATE_WINDOW_SEC` enabled. The application first bounds authentication attempts by trusted source, then hashes the authenticated agent ID and tenant ID so all agent tokens share one agent budget and all tenant agents share one aggregate budget. Random token values never become limiter keys. Redis shares all budgets across instances; failure falls back to bounded per-process protection.
- MCP authentication uses the submitted token hash only as an indexed database predicate. Its result projection is structurally unable to carry either `token_hash` or `password_hash`; do not replace it with full Token/User rows when extending authentication.
- Keep the application HTTP timeouts and size limits enabled. The shipped nginx templates mirror them, but the listener is the final boundary: Web writes accept only bounded URL-encoded forms and MCP requests retain the SDK body limit.
- Do not relax the Web CSP with `unsafe-inline` or cache authenticated SSR/MCP responses. Static asset URLs are not content-hashed and intentionally receive only a five-minute public cache; tenant-bearing responses use `no-store`, including authentication failures.
- Treat application logs as sensitive operational data even though request completion records omit query strings, headers, cookies, bodies, principals, and panic values. Restrict journal/log access and use the server-generated `X-Request-ID` for correlation; inbound request IDs are not trusted.
- Store database, embedding, and MCP credentials outside the release directory with owner-only permissions.
- In production, plaintext dependency traffic is allowed only over loopback. Set remote MySQL and Redis to `verify-full`; the client requires TLS 1.2+, validates the server identity, supports a private CA, and optionally presents an mTLS certificate. Remote Embedding and Atlas endpoints must use HTTPS even when they have no API token because request bodies contain team content. Never use skip-verify, preferred/fallback TLS, or credentials embedded in a URL.
- Keep TLS private keys owner-only, regular non-symlink files. CA and certificate files may be world-readable but must not be group/other writable; the process bounds every PEM file to 1 MiB and fails startup on invalid material.
- Sign production release checksums with an offline Ed25519 key by passing its absolute path as the fourth `package-release.sh` argument. The script rejects symlinked, non-owned, or group/other-readable private keys and never copies the key into the package. Pin the corresponding public key or DER fingerprint through an independently trusted administrative channel; a public key downloaded beside an otherwise untrusted archive is not a trust root. Use `verify-release-signature.sh` before extraction, then run the packaged `verify-release.sh` after extraction. Rotate keys by distributing and pinning the new public key before the first artifact that requires it; retain the old public key while supported releases still depend on it.
- Use `package-release.sh` for production binaries. It embeds a deterministic source-tree digest, while the process computes the SHA-256 of its actual executable at startup. `verify-deployment.sh` checks probe identity consistency; `verify-cluster.sh` rejects `sourceDigest=development` in production and rejects mixed source or binary digests even when version strings match. Compare `binaryDigest` from `-version` with the unpacked file's authenticated checksum. Source and binary digests detect drift; publisher authentication comes from the separately pinned Ed25519 public key.
- Run the new binary with `-check-upgrade` before stopping an existing installation. If migrations are pending, stop every application writer before taking the rollback backup and keep writes stopped through migration and initial acceptance; swapping only the binary is not a valid rollback after the shared schema advances.
- Rotate any Bearer token that appears in chat, shell history, logs, screenshots, or issue reports.
- Restrict `CCS_INGEST_ROOT` to a dedicated read-only tree, or leave it empty to disable Web ingestion.
- Treat every team export as sensitive tenant data. The application requires an administrator, CSRF protection, explicit confirmation, and a persisted meta-audit before querying content; it spools one complete owner-only temporary ZIP per instance and deletes it after the response. Keep `CCS_EXPORT_MAX_BYTES` bounded, download only to controlled storage, and do not attach exports to public issues or ordinary chat. The embedded hashes detect accidental corruption, not a maliciously replaced archive and manifest.
- Keep backup credentials read-only and separate from the restore-rehearsal credentials used on an isolated MySQL server. Both client files must be owner-only and outside the release directory.
- Publish `restore-status.json` only after the isolated target database has been successfully dropped, keep it owner-only, and transport it with the immutable restore report through a trusted administrative channel. The application parses only the bounded receipt; it does not re-read or re-hash the report or archive. A fresh technical receipt proves import, table checks, row/migration enumeration, and cleanup only—not representative Memory/Card/Shared Line semantics or RPO/RTO.
- Keep a second independent, off-host copy of each backup bundle. A checksum proves transport integrity; require an isolated restore report and representative content inspection before relying on a backup for destructive recovery.
